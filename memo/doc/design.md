# mase 方針

方針と、そう決めた理由を書く。理由をまだ聞いていないものは「理由：未記入」とする。

## アプリの位置づけ
- Android 用のシンプルなサウンドエディタにする
- 機能は「1 つの音声ファイルを読み込む・編集する・書き出す」だけにする
  - 理由：シンプルなエディタにするため
  - 複数のファイルを同時に扱う機能は持たない

## 開発言語
- Java で作る
  - 理由：未記入
  - 「Java で」は、「Kotlin や C# ではない」という意味。NDK（C・C++ のコード）を使うことは問題ない

## 動く環境
- Android 14 以降を対象にする
  - 理由：未記入

- targetSdk は 35 にする（compileSdk は 36）
  - 理由：targetSdk を 36 にすると、大きい画面の端末で、画面の向きの固定が Android の側に無視されるため。「画面の向き」の方針を守る

## 作り方
- 画面は、Android 標準の View で作る。AndroidX などの外のライブラリは、今は使わない
  - 理由：Jetpack Compose は Kotlin 用のため使えない。標準の View だけで足りていて、頼るものを増やさずに済む
- 音声データは、メモリの上に、チャンネルごとの 16bit の配列で持つ。一時ファイルには置かない
  - 理由：長さの上限について、RAM の容量の限界が先に来る、とユーザーから聞いているため。足りないときは「メモリが足りない」として読み込みをやめる
  - 使えるメモリを増やすため、アプリの設定で大きいヒープ（largeHeap）を求めている
- 波形を速く描くために、音声データの最小・最大の表を、粗さを変えて何段か持つ（64 サンプルごと、その 8 倍ごと、…）
  - 理由：全体表示では 1 列に入るサンプルが多く、毎回すべてを調べると描くのが遅くなるため
- 編集中の状態（音声データ、開始位置・終了位置、倍率など）は、画面（Activity）の外に持つ
  - 理由：画面が作り直されても、音声データを失わないようにするため
- 音声データを読み書きする処理（読み込み、編集、元に戻す・やり直す、保存）は、画面のスレッドで実行しない。どれも別のスレッドで実行する
  - 理由：長い音声では処理に時間がかかり、画面のスレッドで実行すると、その間、画面が固まるため（ユーザーの指示）
  - 編集の間は、画面の操作を受け付けない。編集している最中の音声データを、ほかの操作が読み書きしないようにするため
  - 画面のスレッドは、編集のスレッドが終わるのを見守る。2 秒で終わらないときは、何 % 終わったかを表示し、利用者がキャンセルできるダイアログを出す（ユーザーの指示）
  - キャンセルされた編集は、何も変えずに終わる。そのために、音声データを新しい内容に切り替えるのは、処理の最後の一瞬にする。長さが変わらない編集は元の配列を書き換えるので、書き換える前の内容を取っておき、キャンセルされたら戻す
  - キャンセルは、編集のスレッドが次に進み具合を知らせるときに効く。すぐには止まらない
  - ダイアログで値を受け取るところまでは画面のスレッドで行い、「OK」の後の処理を別のスレッドに渡す
  - コードでの決まり（新しい編集を足すときに、守ること）
    - 編集は、`MainActivity.runEdit` に渡して、別のスレッドで実行する。音声データを変えない処理（無音区間の選択、再生できるサンプリングレートの調査など）は、`MainActivity.runTask` に渡す
    - 編集の処理は、渡された `Progress` に進み具合を知らせ（`phase`・`step`）、キャンセルを受け付ける。時間のかかるループには、`step` を入れる
    - キャンセルされたときは、音声データ・履歴・コピーバッファを元のままにして、`Progress.Cancelled` を投げる
    - この決まりは、以前は `AGENTS.md` の「作り方の決まり」にも書いていた。同じ内容が 2 か所にあったので、ここにまとめた。`AGENTS.md` には、この節を読む指示だけを残してある
- 音声ファイルの読み込みは、画面とは別のスレッドで行い、その間は「キャンセル」のできるダイアログを出す
  - 理由：長い音声の読み込みで画面が固まらないようにし、途中でやめて元の状態に戻れるようにするため

- 再生は、音声データを少しずつ音の出力（AudioTrack）へ書き込む形にする。再生のたびに出力を作り直す
  - 理由：長い音声でも、再生のためにデータの写しを作らずに済む。作り直せば、サンプリングレートやチャンネル数が変わった後もそのまま使える
- 編集コマンドのダイアログは、前回「OK」で実行したときの値を、次の最初の値にする。最初の値に戻すのは、アプリの起動のときだけ（ユーザーの指示）
  - 値は、編集中の状態（Session）と一緒に持つ（`DialogMemory`）。画面が作り直されても残る
  - 「キャンセル」では覚えない（仮。ユーザーに確かめていない）。理由：試しに開いて、やめただけの値を、次に出さないため
  - 音のミックス・音の挿入・追加で選んだ音声ファイルは、場所（URI）と名前だけを覚え、次にダイアログで使うときに読み直す（ユーザーと決めた。案 A）
    - 理由：中身を覚えると、編集に使えるメモリが減る。場所だけなら、メモリはほとんど使わない
    - 読み直すのは、ダイアログを開いたとき（「OK」のときではない）。理由：表示する情報（サンプリングレートなど）と中身が、必ず一致する。変換方法の行を出すかどうかも、すぐに決まる。読めないことも、すぐに分かる
    - 開くたびに読み込みを待つことになるのは、受け入れた
- 加工するチャンネルを、データファイル名の右の L・R のスイッチで選べるようにする（ユーザーの指示）。オフのチャンネルは加工しない。音声データの長さが変わらない加工だけに効く。無音区間・発音区間の選択では、無音を検出するチャンネルを絞る
  - 長さが変わる加工に効かせないのは、チャンネルごとに長さを変えられないため（と考えた）
  - 貼り付けで、音声データが伸びるときは、オフのチャンネルの伸びた分を無音にする（仮。ユーザーに確かめていない）
  - 音量の最大化の最大のレベルは、オンのチャンネルの中で調べる（仮。ユーザーに確かめていない）。理由：加工しないチャンネルの大きさに引きずられて、思った大きさにならないのを防ぐ
  - スイッチの状態は、編集中の状態（Session）に持つ。起動したときは両方オン
- 縦にスクロールする所は、スクロールバーを常に表示する（ユーザーの指示）
  - 理由：スマートフォンの横画面では、ダイアログやボタン群の下が切れて見えないことが起きやすい。そのことを、分かりやすくするため（ユーザーの説明）。スクロールが止まるとバーが消える、Android の標準の動きでは、切れていることに気づきにくい
  - あわせて、スクロールしなかった編集コマンドのダイアログ（音量の変更など）も、スクロールできるようにした（切れた所を、見られるようにするため）
- 編集コマンドのボタン群は、折り畳めるグループ（ファイル、アンドゥ、選択、編集、選択範囲の加工、全体の加工、音の追加）。「選択範囲の加工」の末尾に、位相反転・逆再生・チャンネル入れ替え、「編集」の末尾に、末尾に追加（ユーザーの指示）に分ける。起動したときは「ファイル」だけを開く（ユーザーの指示）
  - 理由：未記入
  - 縦向きでも横向きでも、同じ作り（見出しのトグルボタンの下に、1 段下げたボタンを縦に並べる）にする。縦向きは画面の下の部分、横向きは右側の列で、縦にスクロールする
- 横向きの画面では、編集コマンドのボタン群を右側に縦に並べる（仮）
  - 理由：横向きは縦が足りず、縦向きと同じ並びでは、開始位置・終了位置の操作や編集コマンドが画面の外に出るため。縦向きは逆に横が足りず、開始位置・終了位置の操作の行が収まらない

## アプリ ID
- Android のアプリ ID は、`Profile.ini` の [AppId] Android を、書いてあるとおりに使う。Java のコードのパッケージ名は、[AppId] Namespace と同じ `net.gorry.mase` にする（ユーザーの指示）
  - 理由：未記入
  - 以前は、[AppId] Namespace に細かい側から書き（`mase.upa.jp`）、逆順にしてアプリ ID（`jp.upa.mase`）にしていた。名前と書く順を、ユーザーが改めた
- パッケージ名は、ソースコードに書いてあるので、ビルドのときに `Profile.ini` から作ることはしない。その代わり、[AppId] Namespace と同じかを確かめて、違えばビルドを止める
  - 理由：食い違ったまま気づかずにビルドされるのを防ぐ
- デバッグ用のビルドは、`Profile.ini` の [AppId] DebugSuffix を、アプリ ID とアプリの表示名に付ける（ユーザーの指示）
  - 理由：未記入（リリース用と別のアプリにして、同じ端末に両方を入れられるようにするため、と見ている。署名が違うので、同じアプリ ID だと、片方を消さないと入れられない。私の解釈）

  - 理由：未記入
- 図案は、画像のファイルではなく、ベクターで持つ。座標は、スクリプト（`tools/make_icon.py`）で計算して書き出す

## ライセンス
- このアプリのライセンスは、Apache License Version 2.0（ユーザーの決定）。全文は、リポジトリ直下の `LICENSE`
  - 理由：未記入
- アプリの情報に、アプリのライセンスと、使っているライブラリのライセンスを表示し、全文も見られるようにする
  - 理由：LGPL のライブラリ（LAME）を組み込んで配るときに、使っていること・ライセンス・ソースコードの入手先を示すため
- ライセンスの全文は、元のファイルを、ビルドのときに APK へ写す。写しをリポジトリに置かない

- ライブラリのまとめのファイルの名前は、`NOTICE`（拡張子なし）にする
  - 理由：`Profile.ini` の [URL] Notice が、`…/NOTICE` を指しているため。はじめは `NOTICE.md` で作っていた

## 外のライブラリ
- C のライブラリを使ってよい。LGPL のライブラリも使ってよい
- 使うライブラリのライセンスは、今は LGPL までに抑える。GPL のライブラリは使わない
  - 理由：コードはすべて公開する予定なので GPL でも困らないが、現状では LGPL までにしておきたい、とユーザーが判断した
- mp3 の書き出しには、LAME（LGPL）を NDK で組み込んで使う
  - 理由：Android には mp3 のエンコーダーが標準で入っていないため
- LGPL のライブラリは、アプリ本体と分けた共有ライブラリ（.so）として組み込み、ライセンスの表示とソースコードの入手先を `NOTICE` に書き、アプリの情報にも表示する
  - 理由：LGPL の条件（利用者がライブラリを差し替えられること、ライセンスを示すこと）を満たすため
- LAME のソースは、リポジトリに入れない。ビルドのときに、配布元のソースパッケージを取ってきて、チェックサムで確かめ、書き換えずにそのままビルドする（ユーザーの指示）
  - 理由：リポジトリの中身の大半（行数で約 67%）が、他人のコードになっていた。配布元のものをそのまま使うので、リポジトリに持つ必要がない
  - git のサブモジュールにはしない
    - 理由：LAME の公式の置き場所は SourceForge（SVN と配布物）で、公式の git リポジトリがない。第三者のミラーを指すことになり、内容や存続を当てにできない
  - 取ってくるのは、ビルドの中で自動で行う。手で置いてあれば、それを使う
    - 理由：手作業を増やさない。一方で、ネットワークのない環境や、配布元が落ちているときにも、ビルドできるようにする
  - 置き場所は、ビルドの結果（`build/`）の外にする
    - 理由：リリースパッケージは、毎回 clean から作る決まり。`build/` の中に置くと、そのたびにダウンロードし直すことになる
  - ビルドに要る設定（config.h）と、Java から呼ぶための橋渡しは、リポジトリに置く。橋渡しを別の共有ライブラリにしておけば、LAME の側（`libmp3lame.so`）だけを差し替えられる
  - 以前は、ライブラリの部分だけを、リポジトリに入れていた（`app/src/main/cpp/lame/`）

- mp3 は、書き出せるサンプリングレート（9 つ）のときだけ選べるようにする。書き出すときにサンプリングレートを変換して合わせることはしない（仮。ユーザーに確かめていない）
  - 理由：保存のときにはサンプリングレートを変換しない、という方針に合わせた。ほかの値で mp3 にしたいときは、先に「サンプリングレートの変更」を使う

## 扱う音声ファイル
- wav・mp3・mp4 を扱う。mp4 は音声トラックだけを扱う
- 形式の名前は、読み込みでは「mp4」、保存では「m4a」と書く。「AAC」は、圧縮方式を説明する所でだけ使う
  - 理由：利用者が目にするのは拡張子。読み込みは、動画の入った `.mp4` も開けるので「mp4」。保存でできるのは、音声だけの `.m4a` なので「m4a」（「mp4」と書くと、動画のファイルができるように読める）。AAC は、ファイルの形式ではなく、中の音声の圧縮方式
  - 理由：未記入

## 内部の音声データ
- サンプルの形式は、入力の形式に関わらず 16bit signed に変換してから持つ
  - 理由：未記入
- チャンネル数（モノラル・ステレオ）とサンプリングレートは、入力のまま持つ。読み込むときに勝手に変換しない
  - 変えるのは、「チャンネル数の変更」「サンプリングレートの変更」「再生レートの変更」を実行したときだけ
  - 理由：未記入
- ファイルに書き出すときは、チャンネル数もサンプリングレートも変換しない。内部で持っている状態のまま保存する。変えたいときは、先に編集コマンドで変える
  - 理由：保存のときには指定できなくてよい、とユーザーが判断した
  - はじめは、ファイル出力時にもチャンネル数・レートを変換できる形を考えたが、改めた
- 内部で持つのは 2ch まで。入力が 3ch 以上のときは、アプリが混ぜたり決めたりせず、読み込むチャンネルを利用者に 2 つまで選ばせる
  - 理由：未記入
- 書き出しの後、書き出した内容で内部の音声データを置き換えるかをダイアログで問う
  - 理由：未記入
  - もとは、ファイル出力時の変換を内部の音声データにも反映するかを利用者に選ばせるためのもの。書き出すときに変換しなくなったので、残すかどうかは未定

## 音声データの長さの上限
- 内部の音声データは「10000 秒未満」「1000000000 サンプル未満」の短いほうまでとし、越える分は末尾を切り捨てて警告を出す
  - 読み込みだけでなく、データの量が増える編集でも同じ確認と警告を使う
  - 理由：データ位置の表示を、秒は「4.5 桁」、サンプルは 9 桁に収めるため
  - この上限で困らないと見た理由：RAM の容量や作業の速さの限界のほうが、先に来るはずの値だから

## 元に戻す
- 編集を元に戻す機能（アンドゥ）と、やり直す機能（リドゥ）を持つ
  - 理由：未記入
- 音声データが変わるたびに、音声データを開始位置・終了位置といっしょに、リングバッファの履歴に保存する
  - 理由：未記入
- 元に戻せる最大回数は決め打ちにせず、設定画面で変えられるようにする。範囲は 0～99、最初の値は 10
  - 理由：未記入
- 履歴を 1 つも保存できないほどメモリが足りないときは、あきらめてその編集をやめる。メッセージで、最大回数を 0 にしてみることを勧める
  - 理由：未記入（最大回数を 0 にすれば、履歴の分のメモリを使わずに編集できるため、と見ている。私の解釈）
- 音声データ全体が変わる編集は、別の持ち方を用意せず、全体を差分として持つ
  - 理由：未記入
- メモリが足りなくなったら、履歴の古いものから捨てる。編集そのものは止めない
  - 理由：未記入
- 履歴の音声データは、できるだけ差分（変わった部分だけ）で持つ
  - 理由：未記入（まるごと持つと、長い音声では 1 回分でもメモリを大きく使うため、と見ている。私の解釈）
- 「再生レートの変更」も、元に戻す対象にする
  - 理由：メタデータの変更として扱うため（未保存の判定と同じ考え方）
- 音声ファイルを読み込んだら、履歴を空にする。書き出した内容で内部の音声データを置き換えたときも、同じく空にする
  - 理由：未記入（置き換えは、読み込んだのと同じに扱うため）
- 元に戻した後に、やり直す以外の編集をしたら、やり直しの分は捨てる
  - 理由：未記入
- 「元に戻す」「やり直す」のボタンは、編集コマンドの「アンドゥ」のグループに置く
  - 理由：未記入
- 編集は、どのコマンドも「ある範囲を、新しい区間に置き換える」という 1 つの形にそろえる。カットは空の区間への置き換え、挿入は長さ 0 の範囲の置き換え、チャンネル数の変更は全体の置き換えになる
  - 理由：履歴の持ち方と、元に戻す・やり直すの処理を、コマンドごとに作らずに済む。長さの上限の確認も 1 か所で済む
- 元に戻す・やり直すの後は、常に未保存の状態にする。保存した時点の内容に戻ったかどうかは調べない
  - 理由：安全な側に倒すため。未保存の音声データを、保存済みと誤って扱わないようにする

## ライトモード・ダークモード
- 画面の配色は、端末の設定に合わせて、自動で変える。波形ビューと再生ビューの中身は、変えない（ユーザーの指示）
  - 理由：未記入（波形ビューと再生ビューの色は、利用者が色の設定で決めるものなので、端末のモードでは変えない、と見ている。私の解釈）
- 配色は、Android の標準のテーマ（端末のモードで切り替わるもの）に任せる。アプリが自分で描く部品（スクロールバー、縦の倍率バーなど）の色だけ、2 つのモードの分を用意する
  - 理由：ボタンやダイアログの色を自分で決めないので、端末の配色とそろう
- ふつうの文字（ラベル、項目名、見出し）は、プライマリの文字色で描く。目立たせない文字用の色（セカンダリなど）は、無効な項目のための色なので、使わない（ユーザーの指示）
  - 個々の文字に色を付けるのではなく、テーマで、ふつうの文字の見た目としてまとめて指定する
    - 理由：コードで作る文字も、レイアウトに書く文字も、指定を忘れずにそろう
- 使っている途中でモードが切り替わったときは、画面（Activity）を作り直す

## 編集コマンド
- ファイルへの出力は「保存」「名前を付けて保存」「選択範囲を保存」の 3 つに分ける。全区間の出力と、選択範囲だけの出力を別のコマンドにする
  - 理由：未記入
- 「保存」は、「名前を付けて保存」を実行済みならその設定を使い、ダイアログを出さない
  - 理由：未記入
- ファイル出力のパラメータでは、サンプリングレートとチャンネル数は選ばせない。選べる形式は、内部の音声データのサンプリングレートで絞る。48kHz までは wav・mp3・m4a、越えたら wav・m4a だけ
  - 理由：未記入（mp3 は 48kHz を越えるサンプリングレートを扱えないため、と見ている。私の解釈）
- 形式ごとに、wav は量子化ビット数（8・16 ビット）、mp3・m4a はビットレートを選ばせる
  - 理由：未記入
- 定義するのは「無音」だけにする。無音は、指定の期間の振幅（最大値と最小値の差）が、指定値以下である状態。無音区間は無音が続く範囲、発音区間は開始位置の左右で無音になる点にはさまれた範囲とし、発音のための条件は別に設けない。期間の長さと振幅の指定値は、設定で変えられる
  - 以前の定義は「サンプル値の微分値が指定値未満、かつサンプル値が 0 付近」で、それに私が「10 ミリ秒以上続く」という決まりを足していた。ユーザーの指示で、期間と振幅の 2 つで決める今の定義に改めた
  - 区間の両端は、見つけた無音の期間の中で、0 にいちばん近い位置にする。同じものがあるときは、前後との差が小さい位置。それも同じなら、無音が始まる側の端は先頭に近い位置、無音が終わる側の端は末尾に近い位置（ユーザーの指示）
    - 理由：未記入（区間の端で切ったり貼ったりしたときに、値の段差ができにくい位置を選ぶため、と見ている。私の解釈）
  - 無音区間・発音区間を探す処理は、Android に依存しないクラス（`SilenceFinder`）にする
    - 理由：パソコンの上で、作った音声で確かめられる
  - 理由：未記入
- コピーバッファの内容を入れるコマンドは、上書きする「貼り付け」と、割り込ませる「挿入」の 2 つに分ける
  - 理由：未記入

- 音量の指定は、dB だけにする。数値の入力欄（小数も受け付ける）と、1dB きざみのスライダーで指定する。範囲は、「音量の変更」が -48～+48dB、「音量の最大化」が -96～0dB（ユーザーの指示）
  - 以前は、「%」と「dB」を切り替えられるようにしていた。ユーザーの指示で、dB だけに改めた
  - 理由：未記入
  - -96dB を下限にしているのは、内部の音声データが 16bit（約 96dB の幅）だからと見ている（私の解釈。ユーザーに確かめていない）
- フェードイン・フェードアウトの音量の時間変化は、リニアではなく対数にする
  - 理由：未記入

- 音程・サンプリングレートを変えるコマンドは、何を保って何を変えるかで 3 つに分ける。「音程の変更」（サンプリングレートを保って音程を変える）、「サンプリングレートの変更」（音程を保ってサンプリングレートを変える）、「再生レートの変更」（データを変えず再生レートだけ変える）
  - 理由：未記入
- この 3 つのコマンドは、選択範囲ではなく音声データ全体を対象にする
  - 理由：未記入
- 「チャンネル数の変更」も同じグループ（「全体の加工」）に置き、音声データ全体を対象にする。変更先は選ばせず、モノラルならステレオ、ステレオならモノラルにする。ステレオからモノラルにするときだけ、「L のみ」「R のみ」「LR 合成」を選ばせる
  - 理由：未記入
- ほかの音を足すコマンド（音のミックス、音の挿入・追加）は、「音の追加」のグループにまとめ、グループの並びの末尾に置く（ユーザーの指示）
  - 足す音は、サイン波・矩形波・音声ファイル（挿入では、無音も）。それぞれの項目と範囲は、ユーザーの指示
- 「音の追加」の音声ファイルは、ダイアログの中の「開く」で選び、選んだときに読み込む（仮。ユーザーに確かめていない）
  - 理由：サンプリングレートの変換が要るかどうかは、ファイルを読まないと分からない。変換アルゴリズムの選択を、要るときだけ出すため（ユーザーの指示：変換する必要がある場合に、アルゴリズムを選ぶ）。3ch 以上のファイルも、その場で断れる
- 「音の追加」のダイアログは、入力に誤りがあるとき、閉じずにメッセージを出す（仮。ユーザーに確かめていない）
  - 理由：項目が多く、閉じてしまうと、入れ直しの手間が大きい。長さは、範囲の端の値に直して実行するのではなく、断る（知らないうちに、違う長さで挿入されるのを防ぐ）
  - ほかの編集コマンドのダイアログ（数値でないときは、何もせずに閉じる）とは、動きが違う
- 「音の挿入・追加」で、入りきらない音声ファイルは、ファイルの末尾を切り捨てる。元の音声データの末尾は、切り捨てない（仮。ユーザーに確かめていない）
  - 理由：足す音のために、元の音が黙って欠けるのを防ぐ。コピーバッファの「挿入」（全体の末尾を切り捨てる）とは、動きが違う
- 矩形波は、帯域を制限しない、単純な形にする（仮。ユーザーに確かめていない）
  - 理由：確認用の信号として、値がはっきり決まるほうが扱いやすい、と考えた。高い周波数では、折り返しの音が混じる
- 波形を作る・混ぜる処理は、画面の部品を使わないクラス（`SoundMixer`）に分ける
  - 理由：パソコンの上で、数値を見て確かめられるようにするため（`Resampler`・`SilenceFinder` と同じ）
- 音程の変更で再生時間を保つかどうかは、ダイアログの「再生時間を維持する」スイッチで利用者に選ばせる。オンのときはタイムストレッチを行う
  - 理由：サンプリングレート変換だけで音程を変えると、音声の長さも変わるため
  - スイッチの最初の状態はオフ（タイムストレッチをしない）
  - タイムストレッチの方式は WSOLA にする（ユーザーから任されて決めた）
    - 理由：時間領域の処理で計算が軽く、自分で実装できる規模に収まる。もう一つの代表的な方式（位相ボコーダー）は FFT が要り、音の立ち上がりがぼやけやすい
  - タイムストレッチとサンプリングレート変換は、短くするほうを先に行う（音程を上げるときはサンプリングレート変換が先、下げるときはタイムストレッチが先）
    - 理由：途中のデータが元より長くならない。以前は「先にタイムストレッチ」としていたが、音程を上げるときに途中のデータが何倍にもなり（そのときの範囲 ±96 では最大 256 倍。今の範囲 ±24 でも 4 倍）、メモリが足りなくなるので改めた
  - サンプリングレート変換とタイムストレッチは、Android に依存しないクラス（`Resampler`）にまとめる
    - 理由：パソコンの上で、数値（雑音の量、周波数、速さ）を確かめられる
- 窓関数付き sinc の窓関数は、カイザー窓にする（ユーザーから任されて決めた）
  - 理由：β の値 1 つで、阻止域の減衰量と切れのよさの釣り合いを調整できる。標準と高品質を、同じコードで値だけ変えて作れる
  - 減衰量は、標準を 80dB、高品質を 100dB とした。内部の音声データが 16bit（約 96dB の幅）なので、高品質はそれを少し上回る値にした
  - sinc の値は、あらかじめ表にしておき、表の間は直線でつないで使う
    - 理由：1 サンプルごとに sin とベッセル関数を計算すると、遅すぎるため
- 長さの上限を越えるかどうかは、実行の後ではなく、パラメータを指定するダイアログであらかじめ表示する
  - 理由：変更の後の長さは、パラメータから実行の前に求められるため
- 変更の後の開始位置・終了位置は、音声の同じ所を指すようにする。長さが変わらなければ元のまま、変わるなら伸び縮みに合わせる
  - 理由：未記入
- サンプリングレート変換アルゴリズムは 1 つに決めず、実行のたびにドロップダウンで選ばせる
  - 理由：未記入
- アルゴリズムは「最近傍」「線形補間」「3 次補間（Catmull-Rom）」「窓関数付き sinc（標準）」「窓関数付き sinc（高品質）」の 5 つ。最初の選択は「窓関数付き sinc（標準）」
  - 理由：品質を重視する用途（sinc）と、速さや荒い音がほしい用途（残りの 3 つ）の両方に応えるため。5 つとも自分で実装できる規模で、外のライブラリに頼らずに済む
  - 決めたときは「NDK が要らない」ことも理由に挙げたが、NDK を使うことに問題はないと分かったので、理由から外した。既存のライブラリ（libsamplerate、SoX Resampler など）に置き換えるかは、決めていない
- サンプリングレート・再生レートは自由な数値にせず、再生するハードウェアで指定できる値から選ばせる
  - 理由：未記入
  - 指定できる値は、システムから取得できればそれを使う。できなければ、起動時に決め打ちの値（48kHz 系、44.1kHz 系、32kHz 系）を総当たりで試す

  - 理由：未記入

- 波形ビューの高さは、割合では決めず、ほかのものを置いた残りにする。縦向きは、下端から「画面の横幅と同じ高さ」の領域を操作のために取る。横向きは、右端から 200dp を編集コマンドに取る（ユーザーの指示）

## 波形ビュー
- 波形ビューに、0 を示す水平線と、時刻を示す垂直線（目盛り）を描く。垂直線は、間が 25dp 以上になる単位まで描き、細かい単位から「薄・中・濃」の色を割り当てる（ユーザーの指示）
  - 理由：未記入
  - 目盛りの色は、名前のとおり、背景（黒）の上で「薄」がいちばん目立たず、「濃」がいちばん目立つ明るさにした。選択範囲の背景（`#404040`）の上でも見えるよう、「薄」をそれより明るくした（私の判断）
- 波形ビューは、指 2 本でのスライドで左右にスクロールし、ピンチで横の倍率を変えられる（ユーザーの指示）
  - 理由：未記入

- 波形ビューのダブルタップで、選択範囲の全体を横幅いっぱいに表示する（ユーザーの指示）
  - 理由：未記入
